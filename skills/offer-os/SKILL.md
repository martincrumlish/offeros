# OfferOS

OfferOS builds complete offer systems from sparse input. Treat the offer as the root object and make every asset support the same buyer, promise, mechanism, and deliverable.

Default to `deep` mode unless the user explicitly asks for a fast or lightweight run. `deep` mode means full strategy, full artifacts, critique/revision passes, real visual assets, a customer-ready PDF, a coded page, a presentation-ready VSL deck, a dashboard, and separate technical and commercial QA. Do not produce a thin scaffold, summary, or outline when the user asks for a complete OfferOS run.

## Operating Principle

Use the intake gate before production. Ask concise questions when missing answers would materially change the offer, buyer, mechanism, proof, price, compliance posture, brand ownership, design source, image style, or checkout path. If a question tool is available, use it for these blocking intake questions. Otherwise ask directly. When the missing fact is non-blocking, make a clear assumption, record it, and continue.

## Run Modes

- `deep`: default. Full workshop-grade build with subagents when authorized, rich copy, real assets, product PDF, VSL deck, dashboard, and QA.
- `standard`: full asset set with fewer iterations and less exhaustive research.
- `fast`: useful draft only. Must be explicitly requested.

If output quality feels light, revise it before moving on. The user should not have to ask for depth after choosing a complete run.

## Standard Full Build

Create these outputs for a full run:

1. `offer-os.json` manifest
2. `offer-intake.json`
3. offer architecture
4. `design.md`
5. primary `assets/logo.png`/`.webp` imagegen-based logo lockup with readable offer name
6. PDF product outline and offer stack
7. `copy-plan.json` using Copy Studio's Modern Brunson long-form framework
8. clean written `copy.md`, internal `copy-blueprint.md`, plus `sales-page-blueprint.json` and `theme.json` rendered from `copy-plan.json`
9. `visual-asset-plan.json` and `visual-asset-plan.md` v2 anchored to copy sections, PDF page archetypes, VSL slide plan, and ad angles
10. coded sales page generated by the OfferOS Page Kit builder
11. supporting images
12. workbook source files and customer-ready PDF product
13. Facebook ads and ad images
14. `email-sequence.json` and launch emails
15. `presentation/vsl-deck-plan.json` and VSL deck
16. delivery dashboard
17. QA notes

Every artifact must be a finished working file where possible. Avoid "strategy-only" substitutes for files the user asked to use, publish, record, or give to customers.

## Commercial Quality Rules

These rules are mandatory in `deep` mode:

- Do not confuse file existence with launch readiness. Technical QA can pass while commercial QA fails.
- When the user asks for generated images or a generated design direction with visual assets, use the `imagegen` skill/tool for bitmap hero/product/ad imagery unless blocked. Do not create or register SVG files for generated visual assets, logos, diagrams, ads, page art, PDF art, or VSL art. Primary sales-page conversion visuals must have their final buyer-facing pixels produced by `imagegen`, not assembled locally. Primary conversion visuals include hero/VSL thumbnail, product bundle, offer-stack bundle, product mockup/product reveal, buyer-situation photo, and ad creatives. For these assets, record `source/provenance: imagegen-final`, `finalPixelsGeneratedBy: imagegen`, `localCreativeOverlay: false`, and `localPostprocess` limited to crop, resize, compression, or format conversion. `imagegen-composite` counts only when the composition itself was performed by imagegen using reference images; local PIL/canvas/HTML/CSS/script composition does not qualify. Do not use Pillow, canvas, HTML/CSS screenshots, or local scripts to add logo, headline text, labels, UI cards, badges, mockups, overlays, or product-stack composition after imagegen. If the logo, text, stack, or composition is wrong, regenerate or edit with imagegen. If imagegen cannot produce an acceptable final asset, mark the artifact `needs_revision` and record the blocker in `qa-notes.md`.
- A paid PDF product must feel deliverable. Match depth to price: a low-ticket paid product generally needs a full workbook/playbook with modules, worksheets, examples, blank templates, implementation steps, and visual render QA.
- The coded sales page must follow the OfferOS direct-response section contract and include `data-offeros-section` markers. Do not substitute a short branded product page for the full sales page.
- A VSL deck must be a presentation-ready `.pptx` PowerPoint artifact. HTML, contact sheets, and browser decks are previews, not the primary deck.
- The delivery dashboard must preserve the standard OfferOS modal/iframe preview template. Theme it; do not reinvent it as a static link grid.
- Every major artifact needs a value audit: would the buyer pay for it, use it without extra explanation, and trust the brand more after opening it?

## Source-Generation Mandates

Build from these source patterns instead of inventing replacements:

- Exact recipes: in deep mode, load `references/exact-build-recipes.md` before creating any buyer-facing artifact. Start with the Build Controller Recipe, then follow the artifact recipes. Do not substitute another production path.
- Studio-owned production: use the plugin-owned OfferOS Studio dispatcher and builders as the production path. Do not create `scripts/build_offer_system.*` in the generated project as the source of truth. Generated projects contain canonical source files plus artifacts; production builders live in this plugin.
- Studio commands: use `scripts/offeros.py` or the underlying studio builders: `build_copy.py`, `build_visual_asset_plan.py`, `build_sales_page.py`, `build_email_sequence.py`, `build_workbook.py`, `build_vsl_deck.js`, `generate_delivery_dashboard.py`, and `validate_offer_outputs.py`.
- Copy Studio: load `references/copy-studio-framework.md`, `references/copy-plan-contract.md`, `references/product-reveal-framework.md`, `references/feature-benefit-rules.md`, `references/objection-matrix.md`, and `schemas/copy-plan.schema.json` before writing sales copy. In deep mode, create `copy-plan.json` first with `framework: "modern-brunson-long-form-v1"`, `standaloneCopyRequired: true`, and `vslDependency: "optional-supporting-asset"`, then run `scripts/build_copy.py` to render clean written `copy.md`, internal `copy-blueprint.md`, and `sales-page-blueprint.json`. `copy.md` is the buyer/seller-facing long-form sales copy used in the delivery dashboard; it must not contain the section blueprint table. `copy-blueprint.md` keeps the section blueprint and framework metadata. The written copy must sell without a VSL. It must include a specific epiphany/new insight before the named unique mechanism, proof/demo before price and offer stack, structured product reveal, feature-benefit-reason bullets, offer-stack value logic, 7+ real objections, and a non-fake urgency basis.
- Sales page framework: load `references/direct-response-framework.md` before page planning for every complete paid front-end offer. The page must render the Copy Studio argument through the canonical section contract: message match, hook/VSL, problem, agitation, failed alternatives, new insight, mechanism, proof/demo, before/after, product reveal, feature-benefit breakdown, how it works, offer stack, guarantee, objections, final close.
- Intake: load `references/intake-gate.md` and create `offer-intake.json` when a complete offer run needs sales-page production. Ask blocking questions when the buyer, promise, mechanism, proof, price, checkout target, or design/image constraints are missing. Default sales-page checkout links to `#checkout` when no external checkout URL is supplied.
- Sales page Page Kit: load `references/page-kit-reference-standards.md`, `references/page-kit-patterns.md`, `assets/templates/sales-page/section-map.md`, `schemas/sales-page-blueprint.schema.json`, and `schemas/theme.schema.json`. Write `sales-page-blueprint.json` and `theme.json`, choosing exactly one approved Page Kit archetype and exactly one approved theme preset, then run `scripts/build_sales_page.py`; do not hand-write `index.html`. The generated page must declare `data-offeros-page-kit="v1"`, `data-offeros-builder="offeros-page-kit-builder-v1"`, and `data-offeros-vsl-placement="main-column-stacked"`. Fill every required `data-offeros-section`; preserve the direct-response hero and buy-box offer-stack contracts exactly, keep proof/demo before the main offer stack, link purchase CTAs to `#checkout` by default, and never include an embedded checkout, order form, payment fields, or credit-card form. Long-form sales pages must not include sticky/hover section navigation or nav links that encourage skipping the copy; use a simple logo/brand header and optional primary CTA only. Eyebrows, buyer filters, and prehead labels are quiet signposts, not loud mini-headlines: no heavy uppercase badge treatment by default. Do not put an eyebrow/pill on every section; default Page Kit section eyebrows use `eyebrowPolicy: "sparse-key-signposts-v1"` and appear only on key signposts such as problem, mechanism, proof, offer stack, and guarantee. When a section eyebrow is used, center-align it with the H2 using `eyebrowAlignment: "centered-with-section-heading"`. Card grids, proof blocks, and offer-stack lists must use Lucide icon markers (`data-lucide`) with CSS fallback rather than plain boxes. Generated images must render in content-hugging constrained buyer-facing frames with `data-offeros-image-display="constrained"`; the outer figure/frame stays transparent and unbordered, with any border/shadow applied to the image itself, so no support image consumes most of the viewport or sits inside a visibly larger colored matte. If the hero already contains the main VSL frame, the later VSL section must not say "Watch this first"; it should explain what the video covers or deepen the argument.
- Sales page type: load `references/sales-page-types.md` before sales copy and choose a page type. Use `direct-response-long-form-vsl` by default for complete low-ticket, cold-traffic, or internet-marketing offers. Record the selected type in `quality.salesPage.pageType`.
- Logo: create one final logo direction before producing the final asset. In deep generated-design runs, use the `imagegen` skill/tool to create exactly one complete logo lockup with symbol plus exact readable offer-name wordmark in the bitmap. Do not create 3 logo options, option sheets, alternate lockups, symbol-only fallbacks, or rough text composites unless the user explicitly asks for options. Reject illustrative marks, page-curl/app-icon graphics, rough cover-art marks, and "mark plus default text" composites. Do not create or register SVG logo files at all. The primary logo must be a horizontal PNG/WebP bitmap lockup at `assets/logo.png`; if a user supplies an SVG logo, convert or recreate it as PNG/WebP before registration. After the single final logo is locked, every downstream imagegen job that needs brand presence must receive `assets/logo.png` as the only logo reference and must use that exact logo, not invent, recolor, redraw, reinterpret, or substitute another logo.
- Visual assets: create canonical `visual-asset-plan.json` plus human `visual-asset-plan.md` v2 only after `copy-plan.json`, clean `copy.md`, `copy-blueprint.md`, and `sales-page-blueprint.json` exist. Split visuals by artifact and anchor every sales-page visual to a real Copy Studio section. Use `mixed-direct-response-v1` by default: mockups are appropriate for product bundle, offer stack, dashboard, and product reveal visuals; mechanism, failed alternatives, proof/demo, objections, and feature specifics should usually use diagrams, comparison visuals, screenshots, structured panels, or restrained supporting imagery. In deep generated-design runs, product bundle/offer-stack/product mockup/hero-VSL/ad creative rows require `source/provenance: imagegen-final`, `finalPixelsGeneratedBy: imagegen`, and `localCreativeOverlay: false` unless the asset is user-provided or licensed. Use `imagegen-composite` only when imagegen performed the reference-image composition and the row also records `imagegenNativeComposite: true`; local composition does not qualify. PDF and VSL need their own supporting visuals/treatments; do not reuse only sales-page imagery as the visual pool. When agents are authorized, dispatch imagegen visual workers after the content blueprint and visual plan exist.
- PDF product: follow the PDF Product Recipe and create `workbook/workbook-blueprint.json`, `workbook/workbook-content.json`, `output/pdf/[slug]-workbook.html`, and `output/pdf/[slug]-workbook.pdf`. Use Gotenberg/Chromium in deep mode and actual final-PDF page render checks. For $30-$99 paid offers, extracted PDF text below 4,000 words or a product that is mostly repeated explanation/blank lines is a failed product, not a warning.
- Emails: follow the Email Sequence Recipe. Create `email-sequence.json` first, then render via Email Launch Studio. Every launch email must include send timing, subject, preview text, campaign role, conversion job, belief shift, primary objection, body copy, CTA, and compliance notes. Repeated boilerplate paragraphs across emails are a failure.
- Dashboard: generate `delivery-dashboard.html` with `scripts/generate_delivery_dashboard.py`. After generation, edit theme variables, logo, imagery, and copy only. Preserve `data-offeros-dashboard="v2-modal"`, modal markup, iframe/image preview behavior, and artifact `data-path`/`data-preview` cards.
- VSL: load `references/vsl-deck-quality.md`, write canonical `presentation/vsl-deck-plan.json`, then create the primary `vsl-deck` as `.pptx` using `scripts/build_vsl_deck.js`/`pptxgenjs` or the Presentations plugin when available and compatible with the same quality contract. Create HTML/contact-sheet output only as `vsl-preview`. The deck artifact `preview` must be browser-safe HTML/image, never the `.pptx` itself.
- Manifest: register source metadata as the artifact is created, including quality fields. Do not backfill optimistic quality scores at the end.
- QA notes: write QA notes from measured outputs and validator/browser results. Do not hard-code page counts, CTA counts, pass/fail status, or warning counts.

If a required source pattern cannot be used, mark the artifact `needs_revision`, record the blocker in `qa-notes.md`, and do not set the manifest status to `complete`.

## Required Sequence

Follow this order unless the user explicitly requests a narrower module:

1. Intake gate and assumptions
2. Offer architecture
3. Design resolver
4. Brand/name refinement
5. Primary imagegen-based logo lockup with readable offer name
6. PDF product outline and offer stack
7. `copy-plan.json` with Copy Studio's Modern Brunson long-form argument
8. clean `copy.md`, internal `copy-blueprint.md`, and `sales-page-blueprint.json` rendered through `scripts/build_copy.py`, plus `theme.json`
9. Artifact-specific `visual-asset-plan.json` and `visual-asset-plan.md` v2 anchored to the Copy Studio source, PDF page archetypes, VSL slide plan, and ad angles
10. Sales-page graphics with provenance recorded
11. Sales page build through `scripts/build_sales_page.py`
12. PDF-specific visuals, `workbook/workbook-blueprint.json`, `workbook/workbook-content.json`, PDF creation, and rendered final-PDF visual check
13. Ads and ad-specific imagegen images
14. `email-sequence.json` and rendered email sequence
15. VSL-specific visuals, `presentation/vsl-deck-plan.json`, and VSL deck
16. Delivery dashboard
17. Technical QA pass
18. Commercial value audit

Do not build downstream visual assets before upstream design/brand decisions and the relevant content blueprint exist. If an upstream asset is missing, create the smallest practical version first.

## Quality Gates

For each major module:

1. Draft the artifact.
2. Critique it against the relevant reference file.
3. Revise weak sections before continuing.
4. Register the artifact in `offer-os.json`.

This is mandatory in `deep` mode for offer architecture, sales copy, sales page, PDF product, ads, emails, VSL deck, and delivery dashboard.

Do not mark `status: complete` until both the module gate and commercial value audit pass. Use `needs_revision` for assets that exist but are thin, placeholder-like, visually weak, or not buyer-ready.

In deep mode, warnings are not shippable. If `validate_offer_outputs.py --strict --no-write` reports any issue or warning, revise the source generator and rerun before handoff.

Browser QA must include sales page, delivery dashboard, and VSL preview at desktop and mobile widths. Horizontal overflow or broken images fail the run.

## Self-Test Requirement

Before handing a revised OfferOS skill or generated offer back to the user, run:

```powershell
python plugins\offer-os\skills\offer-os\scripts\self_test_offer_os_skill.py
```

Maintainers may add `--bad-workspace <path-to-known-bad-output>` when testing against a local regression fixture.

Use the available Python executable. This self-test checks that the skill source contains the exact recipes and that known bad outputs fail for the expected reasons. If the self-test fails, fix the source instructions or validator before asking the user to test again.

## Agent Use

Use subagents only when the user explicitly allows delegation or asks to dispatch agents. Delegate concrete, bounded work that can run in parallel. Keep final integration and QA in the main agent.

For full OfferOS runs with agent authorization, load `references/agent-dispatch.md`. After `offer-architecture.md`, `design.md`, the primary logo lockup, product outline, `copy-plan.json`, clean `copy.md`, `copy-blueprint.md`, `sales-page-blueprint.json`, and `visual-asset-plan.md` v2 exist, dispatch parallel imagegen visual workers for page visuals, PDF visuals, VSL visuals, and ad creatives. Give each worker disjoint output ownership and the same style references so the assets share one visual system. Do not dispatch image workers before the content blueprint exists.

## Completion Standard

A full OfferOS run is complete only when the buyer-facing product exists, the funnel assets exist, the delivery dashboard links/previews the assets, validation has been run, and the final response clearly lists any limits or checks that could not be completed.
